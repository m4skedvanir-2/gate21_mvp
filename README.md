## 概要

Web制作でAPIキーを`.env`に直書きしていた際、AI学習データへの混入による流出事例を知り、開発段階での機密情報管理に課題を感じたことが開発の動機です。

APIキー・認証情報・顧客情報などの秘密資産を暗号化して一元管理し、プロジェクト単位の権限管理・申請制アクセスを組み合わせることで、セキュリティと利便性を両立した業務管理アプリです。

---

## 機能

### 🔐 認証
- **ギミックログイン**: 正しい会社ID（UserID）を入力したときだけ認証フォームが出現。知らなければ入り口にすら気づかない設計
- Argon2によるパスワードハッシュ化
- JWT + リフレッシュトークンによるセッション管理
- 未登録端末からのログイン時はアラート通知（実装予定）
- 2FA（実装予定）

### 📁 プロジェクト管理
- プロジェクト単位でメンバー・資産・タスクを管理
- **申請制アクセス**: プロジェクトへの参加は申請→承認フロー
- 権限管理: オーナー / メンバーの2段階

### 🔒 秘密資産管理
- APIキー・認証情報・トークンなどをプロジェクト単位で管理
- 権限のないプロジェクトの資産は参照不可
- クライアント側・サーバ側の二重暗号化

### 🛡️ 暗号化設計
**クライアント側**
- AES-256-GCMによる暗号化
- 認証済みセッションでのみ復号可能

**サーバ側**
- DEK（Data Encryption Key）で資産データを暗号化
- DEK自体をKEK（Key Encryption Key）で暗号化する2層構造
- 鍵漏洩時の被害範囲を最小化

## セキュリティ設計のこだわり

### ギミックログイン
ハンターハンターの試験会場で正しい注文をしないと本当の試験が始まらない場面を参考に、正しい会社IDを入力したときだけ認証フォームが現れる仕組みを実装。コードを読んでも会社IDはDBにあるため、ソースコードを公開しても安全性は損なわれない。

### 二重暗号化
通信傍受・DB漏洩どちらのリスクにも対応するため、クライアントとサーバの両方で暗号化を実施。サーバ側はDEK/KEKの2層構造により、万が一鍵が漏洩しても被害範囲を限定できる設計。

### 申請制アクセス
プロジェクトへの参加は申請→承認フローを採用。権限のないプロジェクトの資産は取得APIレベルで弾く設計にし、フロントエンドの制御に依存しない。

### 秘密資産変更・削除フロー
プロジェクト単位で秘密資産の変更と削除を申請→承認フローを採用。悪意のある削除や変更を2段階認証を参考に排除する設計。
